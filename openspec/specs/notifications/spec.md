# Notifications Specification

## Purpose

Cross-cutting notification contract for Athlos. Defines the channels, providers, templates, storage, triggers, preferences, and delivery semantics that every other capability (drift-detector, legacy-import, auth-login, scheduler-jobs) builds on to reach operators and administrators.

This spec is the **outbound** notification contract only. Inbound channels (reply parsing, in-app "mark as done" affecting business state) are out of scope. WhatsApp delivery of approval links is defined here for the notification side, but the **approval link lifecycle** itself (token generation, consumption, audit) remains in the `auth-login` spec.

### In scope (v1)

- Email via SMTP using `nodemailer`
- In-app notifications persisted in the `notifications` table and polled by the UI
- WhatsApp as an outbound, out-of-band channel for approval links only (no template system, no inbound)
- Per-operator, per-channel boolean preferences
- Direct, synchronous delivery with try/catch and structured failure logging
- Five mandatory trigger events (drift, import completed, import failed, login from new IP, approval link created)

### Out of scope (v1)

- SMS notifications
- Push notifications (web push, mobile push)
- Notification preferences UI (booleans exist in the data model; no admin screen to edit them)
- Retry queues, dead-letter tables, scheduled retries
- HTML email templates (plain text only in v1)
- Per-tenant branding, localization beyond the single Spanish-locale the club uses
- Delivery webhooks from providers (no inbound ack handling)
- Slack, Teams, or any chat-ops integration

## Requirements

### Requirement: Channel Types

The system MUST support three notification channels in v1: `email`, `in_app`, and `whatsapp`. The system MUST NOT support `sms` or `push` channels in v1.

The `whatsapp` channel is reserved exclusively for delivering approval links. Other events MUST NOT route through `whatsapp` in v1.

#### Scenario: Channel registry contains only the three v1 channels

- GIVEN the notification service is initialized
- WHEN the channel registry is queried
- THEN it MUST contain exactly `email`, `in_app`, `whatsapp`
- AND it MUST NOT contain `sms` or `push`

#### Scenario: Non-approval event is not delivered via WhatsApp

- GIVEN a drift-detected event for the `socios` domain
- WHEN the notification dispatcher resolves the event to channels
- THEN `whatsapp` MUST NOT be among the resolved channels
- AND `email` and `in_app` MUST be the only resolved channels

#### Scenario: Approval link event uses WhatsApp

- GIVEN an approval link was generated by the auth-login service
- WHEN the notification dispatcher resolves this event
- THEN `whatsapp` MUST be among the resolved channels
- AND `email` MAY also be resolved when the approver's `approver_channel` is `email`

### Requirement: Email Provider

The system MUST send email using `nodemailer` over SMTP. The system MUST NOT introduce a transactional email API provider (SendGrid, Resend, Postmark) in v1.

SMTP credentials and the sender address MUST be read from environment variables: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `FROM_ADDRESS`. The system MUST fail fast at startup if any of these is missing in a non-test environment.

#### Scenario: Startup validates SMTP configuration

- GIVEN the notification service starts in the `production` environment
- AND `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `FROM_ADDRESS` are all set
- WHEN the service initializes the email adapter
- THEN initialization MUST succeed
- AND a `nodemailer` SMTP transport MUST be constructed with those values

#### Scenario: Missing SMTP configuration blocks startup

- GIVEN the notification service starts in the `production` environment
- AND `FROM_ADDRESS` is unset
- WHEN the service initializes the email adapter
- THEN initialization MUST throw a configuration error
- AND the service MUST NOT start

#### Scenario: Test environment skips SMTP configuration

- GIVEN the notification service starts in the `test` environment
- WHEN the service initializes the email adapter
- THEN it MUST return the `StubEmailAdapter`
- AND it MUST NOT require `SMTP_HOST` or any other SMTP variable

---

### Requirement: Email Adapter Contract

The email adapter MUST expose a single `send(to, subject, body, context)` method. Adapters MUST live in `packages/integrations/email/`. A `RealEmailAdapter` MUST use `nodemailer`. A `StubEmailAdapter` MUST record every send into an in-memory array exposed as `__emailStub.messages` for test assertions, matching the pattern already used by `StubWhatsAppAdapter`.

#### Scenario: Real adapter delivers via nodemailer

- GIVEN the `RealEmailAdapter` is configured with a valid SMTP transport
- WHEN `send("ops@gorriti.com", "Drift detected", "5 records in CTACTE", { eventId: "..." })` is called
- THEN `nodemailer` MUST submit the message through the SMTP transport
- AND the call MUST return a `messageId`

#### Scenario: Stub adapter records the message

- GIVEN the `StubEmailAdapter` is active in a test
- WHEN `send("ops@gorriti.com", "Drift detected", "5 records in CTACTE", { eventId: "..." })` is called
- THEN `__emailStub.messages` MUST contain an entry with `to`, `subject`, `body`, `context`, and `sentAt`
- AND no network call MUST be made

---

### Requirement: Email Templates

Email bodies MUST be plain text in v1. The system MUST NOT send HTML email in v1. Email subjects MUST be short, action-oriented strings (no template placeholders in the subject).

Templates MUST live in `packages/notifications/templates/<event-type>.txt`. Rendering MUST be plain string interpolation using `{{varName}}` placeholders. The system MUST NOT use Handlebars, EJS, or any template engine in v1.

Templates MUST exist for the following event types: `drift_alert`, `import_completed`, `import_failed`, `login_new_ip`, `approval_link_created` (used only when `approver_channel = 'email'`).

#### Scenario: Drift alert template renders with context

- GIVEN the template `drift_alert.txt` contains `Drift in domain {{domain}}: {{count}} records`
- WHEN the notification service renders the drift alert for domain `socios` with count `12`
- THEN the rendered body MUST be `Drift in domain socios: 12 records`

#### Scenario: Missing template fails the send

- GIVEN a notification event of type `unknown_event` is dispatched
- WHEN the notification service looks up the template
- THEN it MUST throw a `TemplateNotFoundError`
- AND the event MUST be logged as a failed notification

#### Scenario: Templates are plain text only

- GIVEN a template file at `packages/notifications/templates/drift_alert.txt`
- WHEN the file is read
- THEN it MUST NOT contain any HTML tags (`<div>`, `<p>`, `<a>`, etc.)
- AND it MUST be encoded as UTF-8

### Requirement: In-App Notification Storage

The system MUST persist in-app notifications in a `notifications` table. Each row MUST include: `id`, `operator_id`, `event_type`, `title`, `body`, `read_at` (nullable), `created_at`, `metadata` (JSONB). The `metadata` column MUST store the event context (drift counts, import batch ids, IP addresses, approval link ids).

The system MUST support one row per (event, recipient). The system MUST NOT fan a single event into multiple in-app rows per recipient.

#### Scenario: Drift event creates one in-app row per admin

- GIVEN a drift event for domain `ctacte` affects admins `admin1` and `admin2`
- WHEN the notification dispatcher processes the event
- THEN exactly two rows MUST be inserted into `notifications` (one per admin)
- AND both rows MUST have `event_type = 'drift_alert'`
- AND both rows MUST have `read_at = NULL`

#### Scenario: Notification row carries event metadata

- GIVEN a drift event with metadata `{ domain: "ctacte", count: 5, affectedKeys: ["CTA-001", "CTA-002"] }`
- WHEN the in-app row is inserted
- THEN `metadata` MUST contain exactly that JSON object

---

### Requirement: In-App Notification Retrieval

The API MUST expose a `GET /api/notifications` endpoint that returns the authenticated operator's notifications, ordered by `created_at DESC`. The endpoint MUST default to the last 30 days and SHOULD accept `?unread=true` to filter to unread only. The endpoint MUST include `unreadCount` in the response for the UI bell badge.

#### Scenario: Operator lists their notifications

- GIVEN operator `op1` has 3 notifications (1 unread, 2 read)
- AND operator `op2` has 5 notifications
- WHEN `op1` calls `GET /api/notifications` with a valid JWT
- THEN the response MUST contain exactly 3 rows
- AND `unreadCount` MUST be `1`
- AND rows MUST be ordered by `created_at DESC`

#### Scenario: Unread-only filter

- GIVEN operator `op1` has 3 notifications (1 unread, 2 read)
- WHEN `op1` calls `GET /api/notifications?unread=true`
- THEN the response MUST contain exactly 1 row
- AND that row's `read_at` MUST be `NULL`

#### Scenario: Operator cannot read another operator's notifications

- GIVEN operator `op1` calls `GET /api/notifications`
- WHEN the response is computed
- THEN rows belonging to `op2` MUST NOT appear
- AND the query MUST be filtered by `operator_id` from the JWT

---

### Requirement: Mark Notification as Read

The API MUST expose `PATCH /api/notifications/:id/read` that sets `read_at = NOW()` for the specified notification. The endpoint MUST verify the notification belongs to the authenticated operator; otherwise it MUST return `404`. The endpoint MUST be idempotent (calling twice MUST NOT error).

#### Scenario: Marking an unread notification as read

- GIVEN operator `op1` owns notification `notif-123` with `read_at = NULL`
- WHEN `op1` calls `PATCH /api/notifications/notif-123/read`
- THEN the response MUST be `204 No Content`
- AND the row's `read_at` MUST be a non-null timestamp

#### Scenario: Marking an already-read notification is idempotent

- GIVEN notification `notif-123` has `read_at = '2026-06-10T12:00:00Z'`
- WHEN the endpoint is called again
- THEN the response MUST be `204 No Content`
- AND `read_at` MUST remain `2026-06-10T12:00:00Z` (not overwritten)

#### Scenario: Operator cannot mark another operator's notification

- GIVEN notification `notif-123` belongs to `op2`
- WHEN `op1` calls `PATCH /api/notifications/notif-123/read`
- THEN the response MUST be `404 Not Found`
- AND `notif-123.read_at` MUST remain unchanged

---

### Requirement: Notification Preferences Storage

The system MUST persist per-operator, per-channel preferences in a `notification_preferences` table with columns: `operator_id`, `event_type`, `channel`, `enabled`. The system MUST seed defaults on operator creation: every operator receives `in_app` for every event type; admins receive `email` for every event type; non-admin operators receive `email` for `login_new_ip` only; no operator receives `whatsapp` in the default seed.

The system MUST NOT expose a UI to edit preferences in v1. Preferences MAY be edited directly in the database by an administrator.

#### Scenario: Default seed for a new admin operator

- GIVEN a new operator is created with role `ADMIN`
- WHEN the seed runs
- THEN the operator MUST have `in_app` enabled for all 5 event types
- AND `email` enabled for all 5 event types
- AND `whatsapp` enabled for zero event types

#### Scenario: Default seed for a new non-admin operator

- GIVEN a new operator is created with role `OPERATOR`
- WHEN the seed runs
- THEN the operator MUST have `in_app` enabled for all 5 event types
- AND `email` enabled only for `login_new_ip`
- AND `whatsapp` enabled for zero event types

#### Scenario: Preferences filter dispatch

- GIVEN operator `op1` has `email` disabled for `drift_alert` and `in_app` enabled
- WHEN a drift event targets `op1`
- THEN `email` MUST NOT be sent
- AND one in-app row MUST be inserted

### Requirement: Notification Trigger — Drift Detected

The notification dispatcher MUST trigger when the drift-detector reports drift. The system MUST send `email` to all operators with `email` enabled for `drift_alert` AND role `DATA_STEWARD`. The system MUST insert an `in_app` row for every operator with `in_app` enabled for `drift_alert` AND role `DATA_STEWARD`.

Operators whose role is `ADMIN` MUST NOT receive `drift_alert` notifications. Operators whose role is anything other than `DATA_STEWARD` MUST NOT receive them either. The role filter runs BEFORE preferences.

#### Scenario: Drift detected in CTACTE alerts only DATA_STEWARD operators

- GIVEN drift is detected in domain `ctacte` (5 records)
- AND `steward1` and `steward2` (both DATA_STEWARD) have `email` and `in_app` enabled for `drift_alert`
- AND `admin1` and `admin2` (both ADMIN) also have `email` and `in_app` enabled for `drift_alert`
- WHEN the drift-detector emits the event
- THEN `steward1` and `steward2` MUST each receive one `drift_alert` email
- AND `steward1` and `steward2` MUST each have one in-app row with `event_type: 'drift_alert'`
- AND `admin1` and `admin2` MUST receive ZERO emails and ZERO in-app rows for this event

#### Scenario: Non-DATA_STEWARD roles are excluded

- GIVEN an operator with role `OPERATOR` has `email` enabled for `drift_alert`
- WHEN drift is detected
- THEN that operator MUST NOT receive the drift email
- AND no in-app row MUST be inserted for them
- AND this MUST hold regardless of the preference table, because the role filter runs before preferences

#### Scenario: Zero DATA_STEWARD operators → events are still audited

- GIVEN no operator in the system has role `DATA_STEWARD`
- WHEN drift is detected
- THEN zero emails MUST be sent
- AND zero in-app rows MUST be inserted
- AND the drift itself MUST still be recorded in `audit_events` (via the drift package's direct write — see drift-detector spec) so the event is not silently lost

---

### Requirement: Notification Trigger — Import Completed

The notification dispatcher MUST trigger when a legacy import job completes successfully. The system MUST insert an `in_app` row for the operator who triggered the import. The system MUST NOT send email for successful imports in v1.

#### Scenario: Operator is notified that their import completed

- GIVEN operator `op1` triggers the `socios` import
- AND the import completes successfully
- WHEN the dispatcher processes the completion event
- THEN one in-app row MUST be inserted for `op1` with `event_type = 'import_completed'`
- AND zero emails MUST be sent

---

### Requirement: Notification Trigger — Import Failed

The notification dispatcher MUST trigger when a legacy import job fails. The system MUST send `email` to all operators with `email` enabled for `import_failed` AND role `ADMIN`. The system MUST insert an `in_app` row for every operator with `in_app` enabled for `import_failed` AND for the operator who triggered the import.

#### Scenario: Failed import alerts the triggering operator and all admins

- GIVEN operator `op1` triggers the `ctacte` import
- AND the import fails with `LEGACY_UNREACHABLE`
- AND admins `admin1`, `admin2` have `email` and `in_app` enabled for `import_failed`
- WHEN the dispatcher processes the failure event
- THEN `admin1` and `admin2` MUST each receive one `import_failed` email
- AND `admin1`, `admin2`, and `op1` MUST each have one in-app row with `event_type = 'import_failed'`

---

### Requirement: Notification Trigger — Login From New IP

The notification dispatcher MUST trigger when an operator logs in from an IP address not previously seen for that operator. The system MUST send `email` to the logging-in operator (not to admins). The system MUST NOT insert an `in_app` row for login events in v1 (the operator is the recipient and is currently logging in, so an in-app row is low value).

The system MUST consult the `login_history` table (defined by the `auth-login` spec) to determine whether the IP is new. A first login or a login from a previously unseen IP MUST be treated as new.

#### Scenario: Operator logs in from a new IP

- GIVEN operator `op1` has logged in from `192.168.1.10` previously
- AND `op1` has `email` enabled for `login_new_ip`
- WHEN `op1` logs in from `203.0.113.42`
- THEN one `login_new_ip` email MUST be sent to `op1`
- AND the email body MUST include the new IP and a UTC timestamp
- AND zero in-app rows MUST be inserted

#### Scenario: Operator logs in from a known IP

- GIVEN operator `op1` has logged in from `192.168.1.10` previously
- WHEN `op1` logs in from `192.168.1.10` again
- THEN no `login_new_ip` email MUST be sent
- AND the login MUST complete normally

---

### Requirement: Notification Trigger — Approval Link Created

The notification dispatcher MUST trigger when the auth-login service generates an approval link. The system MUST send the link via `whatsapp` (using the existing `WhatsAppAdapter` from the design) when the approver's `approver_channel` is `whatsapp`, and via `email` when it is `email`. The system MUST NOT insert an `in_app` row for approval link events.

The approval link token and URL are produced by the auth-login spec; the notifications service only receives the rendered message and the channel decision. The notifications service MUST NOT regenerate, store, or audit the token.

#### Scenario: Approval link is delivered via WhatsApp

- GIVEN an approval link was generated with `approver_channel = 'whatsapp'`
- AND the approver's phone number is `+5491155550000`
- WHEN the dispatcher processes the event
- THEN the `RealWhatsAppAdapter.send()` MUST be called with the rendered message containing the full approval URL
- AND no email MUST be sent
- AND no in-app row MUST be inserted

#### Scenario: Approval link is delivered via email

- GIVEN an approval link was generated with `approver_channel = 'email'`
- AND the approver's email is `gerente@gorriti.com`
- WHEN the dispatcher processes the event
- THEN one email MUST be sent to `gerente@gorriti.com` using the `approval_link_created` template
- AND the `WhatsAppAdapter` MUST NOT be called
- AND no in-app row MUST be inserted

### Requirement: Synchronous Delivery

The notification dispatcher MUST attempt delivery synchronously in the same request that emits the event, with a per-channel timeout of 5 seconds. The system MUST NOT introduce a background job queue, retry worker, or dead-letter table in v1.

When a channel delivery fails, the dispatcher MUST catch the error, log a structured failure record (event type, channel, recipient, error message), and continue processing the remaining channels. A failed delivery MUST NOT throw to the caller of the dispatcher.

#### Scenario: Email send fails and the request still succeeds

- GIVEN the `RealEmailAdapter` is configured with a transport that throws `ECONNREFUSED`
- AND a drift event triggers for `admin1`
- WHEN the dispatcher processes the event
- THEN the in-app row for `admin1` MUST still be inserted
- AND a structured failure log MUST be emitted with `event_type = 'drift_alert'`, `channel = 'email'`, `operator_id = 'admin1'`, `error = 'ECONNREFUSED'`
- AND the original drift-detector call MUST return success (the dispatcher MUST NOT throw)

#### Scenario: Per-channel timeout enforced

- GIVEN the email transport hangs and does not respond within 5 seconds
- WHEN the dispatcher attempts the email send
- THEN the send MUST be aborted with a `SMTP_TIMEOUT` error
- AND the structured failure log MUST be emitted

#### Scenario: In-app insert is not subject to the 5-second timeout

- GIVEN a single in-app insert against a healthy database takes 50ms
- WHEN the dispatcher inserts the row
- THEN the insert MUST complete in 50ms
- AND the dispatcher MUST NOT impose the SMTP timeout on it (only network I/O calls share the timeout budget)

### Requirement: Event Idempotency

The system MUST accept an optional `eventId` parameter on every dispatch call. When an `eventId` is provided and a notification with that `eventId` already exists in the `notifications` table (or in the audit log of delivered notifications), the dispatcher MUST skip the event without re-sending. The system MUST NOT require idempotency in v1 — it is an at-most-once best-effort layer.

The drift-detector and import jobs SHOULD pass a stable `eventId` (for example, `<job_run_id>:<domain>`) so that retries from the same job run do not produce duplicate notifications.

#### Scenario: Repeated dispatch with the same eventId is a no-op

- GIVEN a drift event with `eventId = 'run-42:ctacte'` was already dispatched
- AND an in-app row exists for `admin1` with `metadata->>'eventId' = 'run-42:ctacte'`
- WHEN the dispatcher is called again with the same `eventId`
- THEN no new email MUST be sent
- AND no new in-app row MUST be inserted

---

### Requirement: Failure Logging

Every notification attempt — success or failure — MUST be logged to the `audit_events` table (defined by the `audit-logger` spec) with: `event_type`, `channel`, `operator_id`, `outcome` (`sent` | `failed` | `skipped`), `error` (nullable), and `timestamp`. The `outcome` field MUST be `skipped` when idempotency dedupes the event.

#### Scenario: Successful email is audited

- GIVEN a drift email is sent to `admin1` successfully
- WHEN the dispatcher completes
- THEN an `audit_events` row MUST be inserted with `outcome = 'sent'`, `channel = 'email'`, `operator_id = 'admin1'`

#### Scenario: Failed email is audited

- GIVEN the SMTP transport throws
- WHEN the dispatcher catches the error
- THEN an `audit_events` row MUST be inserted with `outcome = 'failed'`, `channel = 'email'`, and the error message in the `error` column
- AND the dispatcher MUST continue with the next channel

---

### Requirement: No Inbound Channels

The system MUST NOT accept inbound messages from any channel in v1. WhatsApp reply parsing, email reply parsing, and any webhook from providers MUST NOT be implemented or accepted.

#### Scenario: Webhook endpoint does not exist

- GIVEN the notifications service is deployed
- WHEN an HTTP request arrives at `/api/notifications/webhook` (or any webhook-shaped path)
- THEN the service MUST return `404 Not Found`
- AND no handler MUST be registered

---

## Success Criteria

- [ ] `GET /api/notifications` returns the authenticated operator's notifications with `unreadCount`
- [ ] `PATCH /api/notifications/:id/read` marks notifications as read and is idempotent
- [ ] Drift detected in any domain triggers email + in-app to all ADMIN operators
- [ ] Successful import completion triggers in-app to the triggering operator
- [ ] Failed import triggers email + in-app to ADMINs and in-app to the triggering operator
- [ ] Login from a new IP triggers an email to the logging-in operator
- [ ] Approval link creation triggers WhatsApp (or email, per `approver_channel`) and nothing else
- [ ] Failed email delivery is logged but does not break the originating request
- [ ] Per-operator, per-channel preferences are honored
- [ ] All five event types have plain-text templates under `packages/notifications/templates/`
- [ ] `RealEmailAdapter` and `StubEmailAdapter` exist in `packages/integrations/email/`
- [ ] `StubEmailAdapter` records every send to `__emailStub.messages`
- [ ] Notification attempts (success, failure, skip) are written to `audit_events`
- [ ] No SMS, push, or webhook endpoints exist
